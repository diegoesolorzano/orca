  El problema real y la solución

  El hook post-create de Orca no puede arreglar esto: el smudge falla durante el
  git worktree add mismo. Pero hay una solución limpia que no requiere fork: un
  wrapper de git-crypt configurado en el filtro del repo. Cuando git invoque el
  smudge en un worktree nuevo, el wrapper detecta que faltan las keys, las
  copia desde el gitdir común, y delega al git-crypt real:

  #!/bin/bash
  # git-crypt wrapper: auto-copia keys al gitdir del worktree antes de delegar
  GD=$(git rev-parse --git-dir 2>/dev/null)
  CD=$(git rev-parse --git-common-dir 2>/dev/null)
  if [ -n "$GD" ] && [ "$GD" != "$CD" ] && [ ! -d "$GD/git-crypt" ] && [ -d
  "$CD/git-crypt" ]; then
      cp -R "$CD/git-crypt" "$GD/"
  fi
  exec /usr/local/bin/git-crypt "$@"

  Y en el .git/config del repo (local, no versionado — es donde git-crypt unlock
  ya escribe los filtros), apuntar los smudge al wrapper con ruta absoluta
  (inmune al PATH limitado de apps GUI como Orca):

  filter.git-crypt.smudge = "/Users/diego/.local/bin/git-crypt-wt" smudge
  filter.git-crypt-agente.smudge = "/Users/diego/.local/bin/git-crypt-wt" smudge
  --key-name=agente

  Ventajas: funciona con Orca, con git worktree add manual, con cualquier
  herramienta futura — el problema desaparece del repo entero. Trade-off: hay
  que reaplicar la config si haces git-crypt lock/unlock (reescribe los
  filtros), y es config por repo (nodo-ia y cualquier otro encriptado).
